# 초급 개발자를 위한 실습 교재 다듬기

## 목적과 적용 범위

자바 문법을 학습한 초급 개발자가 실습 순서와 코드의 역할을 이해할 수 있도록 설명을 개선합니다. 개념 강의를 교재에 모두 옮기기보다, 해당 실습을 진행하고 결과를 이해하는 데 필요한 내용을 간결하게 제공합니다.

대상 프로젝트의 `AGENTS.md`, 교재 구성과 관련 모듈을 먼저 확인합니다. 이 프로젝트의 원본은 `practice-book` 아래 Markdown이며, 장·절 번호, 파일 위치 안내, 그림, 코드와 확인 결과의 흐름을 유지합니다. 다른 프로젝트에서는 그 프로젝트의 구성과 독자에 맞춥니다.

## 검토와 반영

- 검토나 제안을 요청받았다면 수정하지 않고, 대상 절·부족한 이유·권장 방향을 제시합니다. 반영을 요청받았다면 해당 범위를 수정하며 이미 승인된 내용을 다시 승인받지 않습니다.
- 요청한 구간의 앞부분도 읽어 용어가 이미 설명되었는지 확인합니다. 처음 등장하는 위치에서 설명하고 이후에는 필요한 경우에만 짧게 상기시킵니다.
- 설명만 다듬는 요청에서는 코드 블록, 프로젝트 소스, API 계약, 설정값과 예제 동작을 보존합니다. 코드 수정이 필요한 불일치는 문장으로 감추지 말고 별도로 알립니다. 코드 변경까지 요청받은 경우에는 관련 교재와 함께 맞춥니다.
- DOCX 재생성, 템플릿 변경, 커밋은 요청 범위에 포함될 때만 수행합니다.

## 필요성에서 시작하는 설명

새 예제를 소개할 때는 학습자가 겪을 상황이나 해결하려는 문제를 먼저 제시하고, 이어서 사용할 방법과 확인할 결과를 설명합니다. 모든 소제목에 형식적인 도입을 붙이지 말고, 독자가 “왜 이 작업을 하는가”를 놓치기 쉬운 전환점에 보완합니다.

예를 들어 테스트의 H2 설정은 설정 항목부터 나열하기보다 “테스트가 실제 회원 데이터에 영향을 주지 않고 같은 조건에서 반복되려면 별도의 DB가 필요합니다”라는 이유에서 시작합니다. MockMvc는 클래스 이름보다 “서비스 테스트만으로는 요청 URL과 HTTP 응답까지 확인하기 어렵습니다”라는 상황을 먼저 설명합니다.

## 낯선 용어와 코드 읽기 돕기

일반적인 자바 기초까지 반복하지 않되, 해당 독자가 아직 배우지 않았을 가능성이 있는 클래스·문법·표현식은 역할을 한두 문장으로 설명합니다. 이름을 쉬운 말로 풀 수 있다면 쉬운 설명을 먼저 쓰고, 코드를 읽는 데 이름이 필요할 때 정확한 식별자를 함께 제시합니다.

검토할 대표 항목은 다음과 같습니다. 모든 장에 이 항목을 새로 추가하는 체크리스트로 사용하지는 않습니다.

- 테스트 도구: JUnit의 테스트 실행 역할, AssertJ의 결과 검증 역할, Mockito의 의존 객체 대체 역할과 MockMvc의 웹 요청·응답 확인 역할을 실제 예제와 연결합니다. 정적 임포트는 클래스 이름 없이 메서드를 호출하는 이유를 설명합니다.
- 로그: `{}`가 값이 들어갈 자리라는 점과 마지막 예외 인수가 상세 오류 정보를 남기는 역할을 설명합니다.
- 예외: 긴 클래스 이름만 나열하지 말고 어떤 실패를 나타내는지, 해당 예제에서 어떻게 처리하고 어떤 응답으로 연결하는지 설명합니다.
- 날짜·시간: 날짜만 다루는지 시간도 다루는지, 예제에서 왜 해당 타입과 출력 형식을 사용하는지 설명합니다.
- 람다·메서드 참조: 전달할 처리 내용을 짧게 표현하는 문법임을 해당 한 줄에 연결합니다. 설정용 람다의 매개변수도 무엇을 설정하는 객체인지 설명합니다.
- 화면 표현식과 보안 객체: `#lists.isEmpty`, `#numbers.sequence` 등의 표현식이나 인증 정보 객체가 실제로 제공하는 정보를 짧게 설명합니다. 프로젝트의 회원 객체와 보안 프레임워크의 사용자 객체를 구분합니다.

내부 실행기나 취소 API처럼 실습 목표에 필요하지 않은 구현 용어는 쉬운 동작 설명으로 바꿉니다. 다만 쉬운 표현으로 바꾸면서 기술적 의미를 단정하거나 바꾸지 않습니다. 예를 들어 타임아웃 응답과 작업 중단·트랜잭션 롤백은 각각의 조건과 결과를 구분하며, 타임아웃만으로 모든 작업이 즉시 중단된다고 설명하지 않습니다.

## 문체와 반복 정리

- 본문은 자연스러운 기술 서적의 ‘~합니다’ 체로 작성합니다. 서로 이어지는 내용은 두 문장, 필요하면 세 문장으로 한 문단을 구성하되, 문장 수를 맞추기 위해 무관한 내용을 합치지 않습니다.
- “설정합니다. 실행합니다. 확인합니다.”처럼 단문만 나열하지 말고 이유·처리·결과의 관계를 연결합니다. 실제 작업 순서나 비교 항목은 목록과 표를 유지합니다.
- “참고 예제입니다”, “프로젝트에는 포함되지 않습니다”처럼 학습에 도움이 되지 않는 반복 안내는 줄입니다. 대신 코드의 삽입 위치, 기존 코드와의 관계, 실행 전제와 필요한 주의사항은 유지합니다.
- 같은 애노테이션·도구의 설명과 중복 표는 최초 학습 위치에 모읍니다. 앞 장으로 옮길 때는 이후 장에서 필요한 맥락이 사라지지 않는지 확인합니다.
- DOCX 변환을 고려하여 문서의 기존 제목·목록·표·링크 관례를 따릅니다. 웹 전용 인터랙션이나 변환되지 않는 내부 앵커에 설명을 의존하지 않습니다.

## 확인과 결과 보고

편집 전 상태와 비교하여 허용된 파일·구간만 변경했는지 확인합니다. 설명만 수정했다면 코드 블록은 개수만 세지 말고 내용과 순서까지 비교하고, 프로젝트 소스가 보존되었는지 확인합니다. 사용자의 기존 변경 사항은 편집 전 상태를 기준으로 보존합니다.

관련 소스를 읽어 메서드 반환값, URL, 설정, 예외 처리와 설명이 맞는지 확인합니다. Markdown 코드 구분자, 로컬 링크, 제목 순서와 `git diff --check`도 확인하되 문장 변경만으로 애플리케이션 실행 검증이 필요한 것처럼 범위를 확대하지 않습니다.

결과는 어떤 장에서 무엇을 이해하기 쉽게 바꾸었는지와 검증 범위를 간단히 알립니다. “코드 미반영”으로 오해할 수 있는 수치 중심 보고 대신 “설명을 다듬었으며 예제 코드와 프로젝트 소스는 요청대로 유지했습니다”처럼 변경 범위를 분명히 표현합니다. 확인하지 못한 일치 여부나 실행 결과는 확인했다고 보고하지 않습니다.
